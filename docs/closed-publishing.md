# Закрытая публикация inpx-web

Для личной библиотеки включите обязательный вход в профиль, используйте HTTPS и ограничьте прямой доступ к порту контейнера. Если библиотека нужна только своим устройствам, можно оставить её в локальной сети и подключаться через VPN без публикации в интернете.

## 1. Подготовьте учётные записи

До включения ограничений создайте профиль с логином и паролем и проверьте вход. Замените стандартный пароль администратора, если он сохранился после обновления старой установки. Для повседневного чтения используйте обычный профиль.

`INPX_ADMIN_PASSWORD` задаёт начальный пароль при создании администратора; изменение этой переменной не меняет пароль уже существующего профиля. На новой установке без неё пароль генерируется и выводится в журнал запуска. Меняйте существующий пароль через управление профилями.

В управлении профилями администратор может заблокировать пользователя. Блокировка завершает его сеансы, отзывает доверие к браузерам и сохраняет полки и прогресс. После разблокировки пользователь входит заново. Если в библиотеке разрешён гостевой доступ, её общедоступные разделы по-прежнему открыты гостям.

## 2. Включите обязательный вход

Добавьте к существующему `docker run`:

```sh
-e INPX_ALLOW_ANONYMOUS_ACCESS=false
```

В Docker Compose добавьте к сервису:

```yaml
environment:
  INPX_ALLOW_ANONYMOUS_ACCESS: "false"
```

Пересоздайте контейнер с прежними постоянными томами и остальными настройками. До входа будут доступны оболочка интерфейса и форма логина. Поиск, книги, обложки, личные данные и OPDS требуют авторизации. `/health`, `/ready` и `/api/index-status` остаются доступны для мониторинга; они не предоставляют доступ к книгам.

Для локального входа доступ к каталогу закрывает `INPX_ALLOW_ANONYMOUS_ACCESS=false`. В Rust при `INPX_AUTH_MODE=local` флаг `INPX_REQUIRE_AUTH=true` также требует входа, даже если гости разрешены. В режиме `INPX_AUTH_MODE=proxy` этот флаг включает проверку внешней авторизации.

В локальном профиле можно включить TOTP в разделе «Двухфакторная авторизация». Подтвердите пароль, отсканируйте QR-код и введите код из приложения. Сохраните выданные одноразовые резервные коды. Настройка отзывает прежние сессии на других устройствах. Уже использованный код нельзя использовать повторно даже в пределах того же интервала.

Доверенные браузеры по HTTPS разрешены по умолчанию на 30 дней. В «Управлении профилями» откройте «Настроить безопасность входа», чтобы отключить доверие или установить срок от 1 до 180 дней. Отключение доверия или изменение срока отзывает уже выданное доверие. При веб-входе пользователь может выбрать «Запомнить это устройство» и ввести текущий код из приложения. Для повторного входа в тот же профиль в этом браузере достаточно пароля. В разделе «Двухфакторная авторизация» пользователь может отозвать доверие ко всем браузерам, подтвердив действие паролем и кодом. Смена логина или пароля, обновление резервных кодов и сброс OTP также отзывают доверие.

В этих же настройках администратор с настроенным OTP может включить «Требовать пароль и OTP для всех». Режим закрывает гостевой доступ. После включения пользователи входят заново, а те, у кого ещё нет OTP, настраивают его при входе. Пока действует разрешённое администратором доверие, для веб-входа с запомненного браузера достаточно пароля. Перед включением задайте логин и пароль каждому профилю. Для публикации через SSO с привязкой профилей управляйте обязательным вторым фактором у провайдера SSO.

В управлении профилями администратор может выбрать «Требовать OTP» для другого локального профиля с логином и паролем. Профиль без настроенного OTP получит QR-код при следующем веб-входе. До завершения настройки доступ к профилю закрыт. Чтобы снова разрешить пользователю отключать OTP, выберите «Отменить требование OTP».

При потере приложения используйте один из резервных кодов для входа. Если они тоже потеряны, администратор может нажать «Сбросить OTP» рядом с другим профилем и подтвердить действие своим паролем и кодом, если TOTP включён у него самого. Пароль пользователя остаётся действительным. Его сессии, резервные коды и пароль OPDS отзываются. Если OTP обязателен для этого профиля, при следующем входе пользователь настроит его заново. Если задан общий пароль OPDS, публикация этого профиля в OPDS выключается, чтобы его полки остались закрыты.

Если единственный администратор потерял оба способа входа, владелец сервера может выполнить одноразовое восстановление при запуске. Для Docker временно задайте `INPX_RESET_ADMIN_PASSWORD=true` и новый `INPX_ADMIN_PASSWORD`, сохраните существующий каталог данных и пересоздайте контейнер. Для standalone используйте `--reset-admin-password` с новым паролем администратора. Вход по новому паролю доступен после запуска. Уберите флаг сброса из конфигурации после первого запуска. Эта операция удаляет TOTP и пароль OPDS администратора и выключает общее требование OTP.

Веб-интерфейс и `/ebook` запрашивают второй фактор, когда он включён в профиле. Выпущенный нативный INPX Reader с полями логина и пароля продолжает работать с профилями без TOTP. Для входа в профиль с TOTP можно открыть веб-интерфейс в браузере Android. Нативному клиенту нужна поддержка `profileTotp` из [контракта API](native-client-protocol.md).

## 3. Ограничьте доступ к контейнеру

Если reverse proxy работает на том же хосте, публикуйте порт только на localhost:

```sh
-p 127.0.0.1:12380:12380
```

В этом случае proxy обращается к `http://127.0.0.1:12380`. Если proxy работает в другом контейнере, подключите оба контейнера к общей выделенной Docker-сети, уберите публикацию `ports` у inpx-web и направьте proxy на `http://inpx-web:12380`. Адрес `127.0.0.1` внутри proxy-контейнера указывает на сам proxy, а не на соседний контейнер.

Для proxy на другом сервере разрешите доступ к порту только с его адреса средствами сети или межсетевого экрана. Уберите проброс `12380` на маршрутизаторе. Во внешнем доступе оставьте HTTPS-вход через proxy; используйте действующий TLS-сертификат и поддержку WebSocket для `/ws` с учётом настроенного префикса URL.

При завершении HTTPS на proxy включите `INPX_TRUST_PROXY=true` и укажите в `INPX_TRUSTED_PROXY_CIDRS` адрес ближайшего proxy, который видит inpx-web, например `172.30.0.2/32`. В Rust 2.0.3 можно указать и IPv6, например `2001:db8:31::49/128`. Это требуется и при локальном входе в профиль. Proxy должен перезаписывать `X-Forwarded-Proto` внешней схемой (`https`) и `X-Forwarded-Host` внешним адресом с портом, если он нестандартный. В nginx для `Host` и `X-Forwarded-Host` используйте `$http_host` или явно заданный внешний адрес. [Caddy по IPv6](../README.md#caddy-по-ipv6)

При публикации контейнера как `12381:12380` upstream по адресу хоста использует `12381`. Прямое подключение по имени контейнера в общей сети использует `12380`. Порт, на котором сам proxy принимает HTTP, задаётся отдельно. Для работающего WebSocket браузер показывает ответ `101` на `/ws`. Если ответ `403`, в журнале inpx-web сообщения `origin mismatch` и `auth failed` различают проверку адреса и проверку внешней авторизации.

## 4. Если нужно закрыть также оболочку интерфейса

Настройте Authelia/Authentik или другую авторизацию на reverse proxy. Чтобы inpx-web также проверял, что запрос пришёл от доверенного proxy с подтверждённым пользователем, добавьте:

```yaml
environment:
  INPX_ALLOW_ANONYMOUS_ACCESS: "false"
  INPX_REQUIRE_AUTH: "true"
  INPX_AUTH_MODE: "proxy"
  INPX_TRUST_PROXY: "true"
  INPX_PROXY_AUTH_HEADER: "Remote-User"
  INPX_TRUSTED_PROXY_CIDRS: "172.30.0.2/32"
```

`172.30.0.2/32` — пример адреса proxy, который видит приложение. Подставьте фактический стабильный адрес или минимальную необходимую подсеть выделенной сети. Не доверяйте произвольным адресам клиентов. Proxy должен удалять или перезаписывать входящий `Remote-User` и передавать имя только после успешной авторизации. Одних переменных контейнера без настроенного механизма входа на proxy недостаточно.

Применяйте авторизацию и передавайте заголовок пользователя для всех HTTP-запросов, а также подключения `/ws`, OPDS, книг и обложек. Если логин профиля совпадает с именем пользователя SSO, опция `INPX_PROXY_BIND_PROFILE=true` позволяет выбирать его автоматически. Иначе потребуется дополнительный вход в профиль.

В Rust режим входа, обязательную авторизацию, доверенные сети и заголовок SSO можно задать в **Управление библиотекой → Доступ и прокси**. Подключитесь к админке через нужный прокси. При смене заголовка сначала настройте на прокси передачу обоих заголовков с подтверждённым именем и переподключитесь. Сервер проверяет действующее соединение администратора перед сохранением. Поля, заданные окружением, доступны для чтения.

Если используете привязку профилей к SSO, включайте второй фактор в политике провайдера SSO. Он проверяет пользователя до передачи `Remote-User`, в том числе при входе в административный профиль.

Health-маршруты по умолчанию исключены из обязательной proxy-авторизации. Чтобы закрыть и их на уровне приложения, задайте `INPX_AUTH_EXEMPT_HEALTH=false` и адаптируйте мониторинг: анонимный health-check больше не получит успешный ответ. Явно включённые исключения для `/metrics` и отдельный токен провайдера Audiobookshelf настраиваются независимо; не публикуйте их без необходимости.

## 5. Подключите OPDS-клиент

OPDS поддерживает Basic-авторизацию по учётным данным профиля с включённой опцией авторизации OPDS либо общему логину и паролю из `opds.user` / `opds.password`. Используйте HTTPS; не помещайте пароль в URL.

Профиль с TOTP использует отдельный пароль OPDS. Создайте его в том же разделе профиля и введите в OPDS-клиенте вместе с логином профиля. При замене или отзыве старый пароль перестаёт работать. Общие учётные данные каталога не открывают персональные полки профиля с TOTP. Когда OTP обязателен для всех, требуется отдельный пароль OPDS из профиля с настроенным OTP.

Многие OPDS-клиенты не умеют проходить браузерную SSO-форму. Для них используйте доступ через VPN или предусмотренную вашим proxy проверку Basic-учётных данных. При включённом `INPX_AUTH_MODE=proxy` даже OPDS-запрос должен приходить от доверенного proxy с подтверждённым `Remote-User`: один Basic-заголовок не отменяет эту проверку. Не делайте анонимное исключение для OPDS, скачивания книг или WebSocket.

## 6. Проверьте результат

- В приватном окне браузера без cookie проверьте, что поиск и скачивание книги требуют входа. При SSO доступ к оболочке также должен требовать авторизации на proxy.
- Убедитесь с другого устройства, что порт `12380` не позволяет обойти proxy.
- После входа проверьте поиск, чтение, скачивание и подключение OPDS-клиента. При SSO проверьте также работу WebSocket и выбор профиля.
- Проверьте, что Docker health-check и мониторинг работают с выбранными ограничениями.

## Индексация и запросы к JS

Файлы `/app…/bundle.…js` содержат код веб-интерфейса; их загрузка необходима для работы страницы. При обязательном входе в профиль оболочка остаётся доступна без входа. При внешней авторизации её закрывает proxy.

Запрет индексации задаётся через `robots.txt` (`Disallow: /`) и HTTP-заголовок `X-Robots-Tag: noindex, nofollow`. Эти правила не заменяют авторизацию, не мешают сканеру игнорировать их и не гарантируют немедленное удаление ранее найденных страниц из поисковиков. Смена домена или префикса URL также не ограничивает доступ.
